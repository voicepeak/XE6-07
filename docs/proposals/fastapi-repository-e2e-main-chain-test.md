# 提案：FastAPI、Repository 与端到端主链测试

## 动机 / 用户故事

将领域、工作流、Agent 和 mock Adapter 接到最小可运行后端，并以端到端测试证明 MS1 Agent 编排主链可从输入追踪到取件。

## 目标用户

- 需要验证主链完整性的开发者
- MS1 集成测试的消费者

## 现有做法及不足

无。当前项目尚未集成后端 API 和端到端测试。

## 本期范围

本期做：

- 最小 API：创建 Project、提交输入、回复确认、查询当前状态、查询 TaskLog
- 实现 Repository 接口与开发/测试存储实现（具体数据库 provider 遵循团队最终决定）
- 注入 Workflow Engine、RuleBasedAgent、Mock Adapter 与 Task Runner
- 提供从上传 STL / GLB 到 `picked_up` 的全 mock 主链
- 让全链路传播同一 `traceId`
- 建立 API、状态机、安全门禁和端到端测试入口

本期明确不做：

- 不实现前端、真实认证、真实对象存储、真实模型生成或真实打印
- 不把 mock 行为伪装为真实打印完成

## 关键决策与依据

### 备选方案

1. 直接暴露内部领域对象，不经过 API 层
   - 优点：快速验证
   - 缺点：无法验证 API 契约和中间件
2. 最小 FastAPI 层 + Repository 抽象 + mock 全链路测试
   - 优点：同时验证 API 契约、状态机和端到端行为
   - 缺点：需要额外 mock 基础设施

### 本期选择

选择方案 2。原因：MS1 需要确认 API 设计、状态机执行和全链路可追踪性，而不仅仅是内部逻辑。

## 基本概念与信息结构

### Project

- 创建后的项目实体，承载输入和状态

### TaskLog

- 记录每次状态变更和 Agent 决策
- 所有记录共享同一 `traceId`

### Repository

- 领域对象的持久化接口
- 开发/测试阶段使用内存或轻量存储实现

## 原型 / 演示

不适用。

## 验收标准

### 例子 1：成功主链（STL 上传到取件）

- 现状：没有 API 或全链路测试。
- 提议后的行为：通过 API 创建 Project、提交 STL 输入；RuleBasedAgent 路由经过上传、审计、切片、确认和 mock 打印，最终到达 `picked_up`。
- 验收：端到端测试覆盖完整路径，所有 TaskLog 记录共享同一 `traceId`；最终状态为 `picked_up`。

### 例子 2：审计未通过阻断

- 现状：无。
- 提议后的行为：提交一个审计失败的模型输入，主链在审计阶段被阻断，状态不会进入切片或打印。
- 验收：API 查询显示当前状态停留在审计失败阶段，TaskLog 记录阻断原因。

### 例子 3：未确认打印阻断

- 现状：无。
- 提议后的行为：到达需要确认打印的步骤，用户未回复确认时，状态不会进入打印阶段。
- 验收：TaskLog 显示等待确认状态，后续步骤未被执行。

### 例子 4：设备离线阻断

- 现状：无。
- 提议后的行为：模拟打印设备离线，状态不会进入打印或取件阶段。
- 验收：API 返回设备离线状态和可理解的消息，TaskLog 记录离线事件。

### 例子 5：非法状态跳转

- 现状：无。
- 提议后的行为：直接调用 API 尝试从非相邻状态跳转（如跳过审计直接打印），请求被拒绝。
- 验收：API 返回 4xx 错误，TaskLog 不产生新记录或记录被拒绝的原因。

### 例子 6：README 说明

- 现状：无。
- 提议后的行为：README 说明 mock 服务的启动方式、可测试的范围和已知边界。
- 验收：按 README 步骤可启动服务并运行端到端测试。
