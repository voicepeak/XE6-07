# 提案：统一管理员身份与基础权限

## 动机 / 用户故事

MVP 阶段需要可区分的登录身份来支持私有模型、收藏、Fork、提交发布和举报。同时需要后台管理能力来审核模型、处理举报、管理设备和确认取件。本期只设置普通用户和统一管理员两类身份，后续再决定是否拆分角色。

## 目标用户

- 普通用户（user）：管理自己的模型、发布、收藏、Fork、举报和打印操作
- 统一管理员（admin）：执行模型审核、下架、举报处理、设备异常处理和取件确认

## 现有做法及不足

无。当前没有身份体系或权限控制。

## 本期范围

本期做：

- 两类身份：普通用户（user）和统一管理员（admin）
- 管理员职责：审核/驳回/下架公开模型、查看处理举报、处理打印异常和取件确认
- 管理员可查看上述操作所需的后台列表和详情
- 普通用户不能访问管理后台，不能通过构造链接或请求绕过权限
- 所有私有模型、资源和任务按 `ownerId` 或明确授权范围执行对象级权限校验，知道对象 id 不代表有权访问
- 用户需要可区分的登录身份（具体认证方式后端实现时统一决定）
- 初始管理员账号由项目部署时指定
- 普通用户不能自行提升为管理员
- 每次管理操作保留操作人、动作、目标、前后状态、结果或原因以及 `traceId`
- 未登录用户：可浏览公开内容，不能访问私有内容，不能收藏、Fork、发布、举报或发起管理操作

本期明确不做：

- 不做注册、找回密码、邮箱验证、OAuth 等完整账号系统
- 不做用户资料页、头像、昵称编辑或社交主页
- 不做管理员任命、撤销、角色分配的后台界面
- 不做封号、禁言、账号删除和信用体系
- 不做多层级管理员或细粒度权限矩阵

## 关键决策与依据

### 备选方案

1. 不区分角色，所有登录用户拥有同等权限
   - 优点：实现最简单
   - 缺点：无法控制敏感管理操作
2. 普通用户 + 统一管理员
   - 优点：MVP 即可支持管理闭环，后续可按需拆分角色
   - 缺点：管理员职责范围较宽

### 本期选择

选择方案 2。原因：MVP 阶段管理操作数量有限，统一管理员可覆盖全部需求；后续可从 admin 拆分为 content_reviewer、printer_operator、account_admin 等细分角色，已有功能的业务结果不受影响。

## 基本概念与信息结构

### 身份角色

```
user   - 普通用户
admin  - 统一管理员
```

### 权限规则

```
user:
  - 管理自己的模型、发布申请、收藏、Fork、举报和打印相关操作
  - 只能读取或操作自己拥有、被明确共享或已经公开的对象
  - 不能进入管理后台
  - 不能审核、下架、处理举报或确认其他用户的取件

admin:
  - 具备 user 的基础能力
  - 可执行模型审核、下架、举报处理、设备异常处理和取件确认
  - 每次管理操作写入结构化管理日志
```

### 对象级授权

- 受保护对象至少包含模型、Asset、可打印性检查任务、切片任务和打印任务。
- 服务端根据当前身份、对象 `ownerId`、公开状态和明确授权范围决定访问结果；不得把 `modelId`、`assetId` 或 `taskId` 当作访问凭证。
- 对无权访问的私有对象返回 403，或为避免泄露对象是否存在而统一返回 404。

### 管理操作日志

- `operatorId`: 操作管理员
- `action`: 审核、驳回、下架、举报处理、设备异常处理或取件确认
- `targetType` / `targetId`: 被操作对象
- `before` / `after`: 操作前后状态
- `result` / `reason`: 操作结果及原因
- `traceId`: 对应请求链路
- `timestamp`: 操作时间

### 未来角色拆分（本期不做）

```
content_reviewer   - 内容审核员
printer_operator   - 设备管理员
account_admin      - 账号管理员
```

## 原型 / 演示

### 演示流程

```
普通用户提交模型审核
-> 模型进入待审核状态
-> 普通用户不能访问审核列表

管理员登录
-> 进入审核列表
-> 审核通过或驳回模型
-> 系统记录管理员和操作时间

普通用户尝试直接打开审核后台链接
-> 被拒绝访问
```

## 验收标准

### 例子 1：管理员审核模型

- 现状：无身份体系。
- 提议后的行为：管理员登录后可以访问审核列表，审核通过或驳回模型。
- 验收：审核操作被记录，包含操作人（admin）和操作时间；模型状态更新为通过或驳回。

### 例子 2：普通用户被拒绝管理操作

- 现状：无。
- 提议后的行为：普通用户尝试访问管理后台或调用管理 API 时被拒绝。
- 验收：HTTP 响应返回 403 或等效的权限拒绝状态；不暴露管理数据。

### 例子 3：普通用户不能自我提升

- 现状：无。
- 提议后的行为：普通用户不能通过前端参数、直接链接或重复请求把自己提升为管理员。
- 验收：任何形式的角色提升请求被服务端拒绝。

### 例子 4：未登录用户限制

- 现状：无。
- 提议后的行为：未登录用户可以浏览公开内容，但不能访问私有数据、收藏、Fork、发布、举报或管理操作。
- 验收：未登录请求私有数据或需要身份的操作时返回未授权状态。

### 例子 5：跨账号私有资源隔离

- 现状：已登录用户可能通过猜测或获得其他用户的对象 id 访问私有资源。
- 提议后的行为：服务端对每次模型、Asset 和任务访问执行对象级授权。
- 验收：用户 A 使用用户 B 的 `modelId`、`assetId`、检查任务 id、切片任务 id 或打印任务 id 发起读取、下载或写操作时均返回 403/404，且响应不包含用户 B 的私有元数据。

### 例子 6：管理操作可追溯

- 现状：无。
- 提议后的行为：模型审核、下架、举报处理、设备异常处理和取件确认均写入结构化管理日志。
- 验收：分别执行模型审核、模型下架和取件确认后，每条日志均包含 `operatorId`、`action`、`targetType/targetId`、`before/after`、`result/reason`、`traceId` 和 `timestamp`。

### 例子 7：管理员处理举报

- 现状：无。
- 提议后的行为：管理员可查看举报列表，处理举报并在必要时下架模型。
- 验收：举报处理记录包含操作人；下架操作同步记录。
