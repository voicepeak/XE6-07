# 提案：图生模型兜底链路

## 动机 / 用户故事

当前图生模型优先走本地部署，但本地模型可能出现失败、超时、显存不足或服务异常，导致任务中断。需要保证本地模型不可用时任务仍能继续，降低单点失败风险，提升整体成功率和用户体验。

## 目标用户

- 提交图生任务的用户
- 运维和监控任务成功率的开发者

## 现有做法及不足

无兜底机制。本地模型失败时任务直接中断，用户需要手动重试或等待服务恢复。

## 本期范围

本期做：

- 本地模型失败检测：捕获超时、异常、显存不足等失败场景
- 超时 / 异常捕获与分类
- 自动切换第三方 API 完成图生任务
- 兜底原因记录：每次切换时记录触发原因
- 本地与外部结果统一：两种来源的输出使用相同的格式，后续流程无感知

本期明确不做：

- 不做多级兜底链（如 API A 失败再切 API B）
- 不做本地模型预热或弹性扩容
- 不做用户手动选择模型来源

## 关键决策与依据

### 备选方案

1. 本地模型失败时直接返回错误
   - 优点：实现零成本
   - 缺点：任务中断，用户需要手动重试
2. 本地优先、API 兜底
   - 优点：本地可用时享受低延迟，不可用时自动无缝切换
   - 缺点：需要维护 API 调用链路和结果统一逻辑

### 本期选择

选择方案 2。原因：在本地模型稳定性不足的阶段，兜底机制可以避免单点失败导致用户流失。

## 基本概念与信息结构

### FallbackRecord

- `reason`: 兜底触发原因（超时 / OOM / 服务异常等）
- `source`: 实际完成任务的来源（local / api）
- `timestamp`: 记录时间

## 原型 / 演示

不适用。

## 验收标准

### 例子 1：本地模型成功

- 现状：本地模型正常完成任务。
- 提议后的行为：本地模型可用时优先使用本地，不触发兜底。
- 验收：结果标记来源为 local，FallbackRecord 不产生。

### 例子 2：本地超时触发兜底

- 现状：本地模型超时后任务中断。
- 提议后的行为：本地调用超时后自动切换到第三方 API，API 结果正常进入后续流程。
- 验收：结果标记来源为 api，FallbackRecord 记录原因为超时；后续流程（如检查）可正常消费结果。

### 例子 3：本地显存不足触发兜底

- 现状：OOM 导致任务中断。
- 提议后的行为：捕获 OOM 异常，自动切换到第三方 API。
- 验收：FallbackRecord 记录原因为 OOM；API 结果格式与本地一致。

### 例子 4：不出现死循环

- 现状：无。
- 提议后的行为：API 调用也失败时，不应再次尝试本地或循环切换。
- 验收：兜底失败后返回明确错误，不在本地和 API 之间反复切换。

### 例子 5：兜底原因可统计

- 现状：无。
- 提议后的行为：每次兜底记录原因和发生时间。
- 验收：可按时间范围和原因类型查询兜底统计。
